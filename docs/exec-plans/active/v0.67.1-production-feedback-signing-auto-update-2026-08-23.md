## 用户问题、争议与本轮取舍

### 用户原始问题

1. 2026-08-23 的用户截图显示：升级到 `0.67.1` 后，GLM (CN) 的“添加模型”弹窗把 GLM-5.3 标成“已添加”，但 Models/模型选择仍找不到它；旧 GLM-5-Turbo 仍存在。
2. 最近 production Sentry 出现多类报错，需要区分真实产品故障、环境/退出噪声、遥测隐私违约和分类不足。
3. 用户明确要求这次把软件签名与自动更新做完整，不再只提示用户去 GitHub 手工下载。

### 必须先改判的历史结论

- B-031 虽然有 v0.67.1 的 targeted/full/build/isolated UI/CI 证据，但新截图来自**真实 0.67.1 升级用户**，因此只能保留历史证据，不能继续把用户路径写成已关闭。B-031 从 `Shipped fix` 重开为 `Shipped but production path failed`。
- 旧计划曾决定保持手动更新；用户在 2026-08-23 明确改变产品方向。该旧决定不再阻止实现 native updater，但仍保留“preview 不能进入 stable feed、签名未闭环前不能自动安装”的安全理由。
- 当前 macOS Developer ID 签名链已经存在，不应推倒重做；“彻底签名”在此基础上补 notarization/stapling、Windows Authenticode、发布资产/更新元数据身份一致性，以及 Linux 的诚实信任边界。

### 本计划采用的产品定义

- “自动更新”默认定义为：应用自动检查 stable 更新、后台下载并验证、准备完成后提示用户重启安装。首版**不强制静默重启**，活动 chat/bridge/task 不被 updater 擅自终止。
- Settings > About 保留“检查更新”；native 更新不可用或失败时退回当前按平台选择 GitHub Release 资产的手工路径，不显示假成功。
- 当前用户决策是 macOS 完成自动安装闭环，同时 stable tag 发布 Windows/Linux 手动安装包。Windows/Linux 关闭 official updater provenance 且不发布 updater metadata；preview 仍为 Mac-only。Windows signer 全缺时允许明确未签名的手动包，部分配置失败，全配置时恢复 Authenticode verifier。
- GLM 修复、Sentry P1 与 updater 可以拆成不同 patch release；不得为了等大功能而延后隐私或启动阻断修复。

## 实施前事实基线（2026-08-23 取证时）

> 本节保留开工时的仓库证据，用于解释修复为什么需要发生；它不是当前 working tree 的状态。当前实现与验证结果以顶部状态、remediation 表、Smoke Ledger 和决策日志为准。

### GLM / B-031

- `search-models` 的 catalog-only 分支用长期 stable `modelId`（GLM 当前为 `sonnet`）和变化的 wire `upstreamModelId`（`glm-5.3[1m]`）。`getPresence()` 只要本地行命中 stable 或 wire 任一身份就返回 `alreadyAdded=true`。
- 因此遗留的 `sonnet → glm-5-turbo/5.2/sonnet` 行也可能把 GLM-5.3 候选标成“已添加”，但它并不证明当前 SKU/wire 已经落库或已在 picker 可用。
- `mergeCatalogManagedModels()` 只更新 `source='catalog' && user_edited=0 && enable_source NOT IN manual_*` 的行。共享 stable id 的非 catalog-managed 行只会让该 stable slot 跳过更新；真正阻止新行插入的是“stable id 尚不存在、但 wire/upstream id 已被其他行占用”。两种路径都可能让真实旧安装卡在旧 wire，但 classifier、迁移条件和反例必须分轴设计，不能把 stable-id 命中误写成插入阻断。
- isolated fixture 基础设施首次提交于 v0.58.1，并非 v0.67.1 新增；v0.67.1 hotfix 扩展/复用了它来验证 pristine catalog、hidden、direct-wire、并发等路径，但没有用这次受影响用户的真实 row shape 完成升级 smoke。旧“已关闭”结论缺的正是这条证据。

### Sentry（上一轮只读快照，Phase 0 必须重跑）

> 当前本地环境没有 `SENTRY_AUTH_TOKEN`；下面是上一轮只读分析的 handoff 基线，不冒充 2026-08-23 的新查询。Claude 必须用本地只读 token 重跑同口径，禁止把 token 打印、提交或粘贴进聊天。

- **隐私 P1**：真实 0.67.1 JS/Electron/native event 仍出现服务端推断 geo；native minidump 可含本机绝对路径。前者说明 null-IP/project setting 至少一层未形成实际结果；后者可能绕过 JS `beforeSend`，不能用 sanitizer 单测冒充解决。
- **SQLite P1**：`CODEPILOT-DESKTOP-24` 的 `database disk image is malformed` 在 macOS/Windows 启动 `getDb()` 路径出现，上一轮看到近期约 33 次；当前没有用户可见的完整性诊断、保全、恢复/导出闭环。
- **ABI P1**：`CODEPILOT-DESKTOP-36` 在 Windows 出现 better-sqlite3 模块 ABI `143`、运行时需要 `137`。CI 现在用 `ELECTRON_RUN_AS_NODE=1` 验证 native module，而生产由 Electron Main `utilityProcess.fork()` 启动 Next，门禁没有证明同一运行形态。
- **P2 候选**：Marketplace stream 在取消后 `Controller is already closed`；Provider quick action / memory extract 报错大量落到 `unknown`；Windows `spawn EPERM` 未收敛成工具结果；Windows logoff 的 `0x40010004` / `0xC000026B` 被当产品故障；少量 GPU native crash 缺 app frame，不能直接归因或全局禁 GPU。

### 签名与更新

- `electron-builder.yml` 已有 GitHub publish provider、macOS `dmg+zip`、Windows NSIS、Linux AppImage/deb/rpm；`electron-updater` 以 `^6.8.3` 进入 production dependencies，但除 disabled stub 外没有真实调用方，启用前必须 exact pin 并按该版本合同验证。
- `electron/updater.ts` 当前明确 `DISABLED`；`electron/main.ts` 没有初始化它，`electron/preload.ts` 也没有 updater bridge。Renderer 的 `useUpdateChecker` / dialog/type 只是未接通的 latent contract，Electron 内实际走 `/api/app/updates` 手工下载 fallback。
- stable workflow 所有 package step 都使用 `--publish never`；在当前 builder/publish 配置下它仍会生成 update metadata。丢弃发生在双层白名单：macOS、Windows、Linux 三个 platform job 的 `upload-artifact.path` 都漏掉 `latest*.yml`/blockmap，central release job 的 asset glob 又再次排除它们；当前 GitHub Release 因而不是可用的 electron-updater feed。
- macOS stable 已有 Developer ID + exact Team ID fail-closed gate，但 `notarize:false`；没有 Apple notarization/stapling 证据。
- Windows NSIS/EXE 没有 Authenticode 凭据与 final signature verifier。签名主体必须跨版本稳定，否则 Windows updater 的 publisher 校验不能成立。
- 官方合同参考：[electron-builder Auto Update](https://www.electron.build/docs/features/auto-update/)、[macOS notarization](https://www.electron.build/docs/notarization/)、[Windows code signing](https://www.electron.build/docs/features/code-signing/code-signing-win/)、[Apple notarization workflow](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)。

## Phase 1：GLM-5.3 真实升级路径

### 用户会看到什么

- GLM-5.3 只有在当前 SKU 确实存在且可选择时才显示“已添加”。
- 可证明是旧内置目录行时，打开 Models 后安全升级为当前 GLM-5.3；真正的用户自定义冲突不会被静默覆盖，而会显示“旧目录待升级/身份冲突”的明确恢复动作。
- hidden 仍可“重新启用”；不会制造同一 upstream 的双行，也不会破坏 session pin、排序和手动能力设置。

### 本阶段明确不做什么

- 不让 Models GET 按 stable id 或 `source` 猜测迁移，不把 `user_edited=1` 粗暴等同于可覆盖或不可覆盖，也不删除/禁用 ambiguous/manual 行来制造“修好了”的表象。GET 只允许对完整历史 fingerprint 命中的系统行执行幂等 compare-and-swap。
- 不顺带改变其他 provider 的 stable identity、默认模型或推理强度合同；任何 schema 变化都必须是此迁移所需的最小 additive 变更。

### 技术取舍

- 不再用 `alreadyAdded:boolean` 压扁 SKU 状态。至少区分 `current_enabled`、`current_hidden`、`legacy_upgrade_available`、`identity_conflict`、`missing`。
- 自动迁移只允许“可证明属于历史内置目录”的行：exact provider preset + stable id + upstream/display/capability 与已发布旧 catalog fingerprint 一致。classifier 必须分别处理“stable slot 已有非 catalog-managed 旧行，因此跳过更新”和“stable slot 不存在、upstream 被其他行占用，因此阻止插入”；`user_edited=1` 不能单独证明用户所有权，也不能单独证明可覆盖，需要字段级 provenance/旧目录反证。
- 对 ambiguous/manual 行不得借 Models GET 写入。提供 preview/确认后的 replace/keep 选择；如果需要新 schema，遵守 additive + conservative backfill，并先更新 `DatabaseSchema.md`。

### 执行清单

- [x] 用已发布旧 catalog 的 gen-0 `GLM-4.7`、后续 `GLM-5-Turbo`/`GLM-5.2` 与 `GLM-4.5-Air` fingerprint 写 failing-then-passing 完整目录 fixture，覆盖 sonnet/haiku 的真实升级历史并保留各世代旧 opus 行；真实 Turbo 指纹是 upstream=`sonnet`，删除 git 历史无法证明的 upstream=`glm-5-turbo` 猜测。真实用户行仍待脱敏对账。
- [x] 把 candidate presence 从 stable-slot 命中升级为 SKU-aware 五态；stable id 相同但 wire 仍为旧世代时不再算 current。
- [x] 增加 legacy catalog classifier/迁移事务；覆盖 stable-slot、upstream occupancy、旧 upstream/display/capability、source/user_edited/enable_source 与 same-upstream direct-wire 反例。
- [x] 事务幂等、并发安全、保留非目标行数量与用户排序；不 delete、不静默 disable、不将 ambiguous 当成功。
- [x] Models API、search API、Runtime group、Settings/Composer 共享/验证同一 identity contract。
- [x] UI 对 current/hidden/legacy/conflict/missing 使用明确状态和真实恢复动作。
- [x] 更新 `ProviderManagement.md`、`ModelDiscovery.md` 与 B-031 的实现状态。
- [ ] 真实受影响用户从 0.67.1 升到候选版本后完成一次只读前后 diff + UI smoke；没有这条不得关闭 B-031。

### 本地结果

- `legacyFingerprints` 只允许 upstream/display/capabilities 全字段吻合且无用户所有权信号的旧行升级；历史 `source='manual'` 不再被单独当成用户所有权。fixture 分别使用 gen-0 与后续真实三行旧库，结果均为 sonnet/haiku 原位升级、非目标 opus 保留。
- upstream wire 被其他行占用或字段有歧义时返回 `identity_conflict`，不覆盖、不补重复 SKU；若当前 canonical SKU 已存在，则额外旧行不再把可用模型整体降级为 conflict。Add Model 不再用一个“已添加”吞掉 hidden/legacy/conflict，并实际消费冲突 model ids 给出恢复动作。

- [ ] Windows logoff 的 `0x40010004` / `0xC000026B` 只在已证明 session shutdown/logoff 时归 expected lifecycle；同码非退出场景仍保留故障，不能全局 ignore。

## Phase 7：验证、渠道晋级与恢复

### 用户会看到什么

- 0.67.1 用户仍需手工安装首个 updater-capable macOS 版本；后续版本才具备原生自动更新。用户本轮选择跳过 RC-A → RC-B 实机验收，发布汇报必须明确这项风险。

### 本阶段明确不做什么

- 不把 0.67.1 手工下载安装冒充 native auto-update，也不把未执行的 clean-machine/RC-A → RC-B 验收写成通过。
- 不做不可审计的 10%/50%/100% 百分比放量；stable 全量发布后不修改 metadata 或复用 tag/version，恢复只发更高 patch。

### 自动门禁

- targeted：GLM identity/DB/routes/UI、Sentry sanitizer/classifier/utility、updater state/IPC/channel/release assets、signing policy。
- full：`npm run test`。
- production：`npm run build` + `npm run electron:build`。
- package CI：macOS arm64/x64 + universal updater；真实 Electron utility process health、0 source map、签名/公证、metadata/hash 引用。
- 文档：`npm run lint:docs-drift`、`npm run lint:hooks`、`git diff --check`。

### 真实升级矩阵

| From → To | 平台/安装形态 | 必测场景 | 通过条件 |
|---|---|---|---|
| 0.67.1 → RC-A | macOS arm64/x64 DMG/ZIP | **手动**下载/安装 bootstrap、Gatekeeper、Safe Storage、数据/会话保留 | RC-A 启动且 updater 可用；无重复 keychain 授权，旧数据完整；证据不标成 auto-update |
| RC-A → RC-B | macOS arm64/x64 | 后台检查/下载、用户确认重启安装、签名/公证/metadata 验证 | RC-B 启动且版本正确；失败可保留 RC-A 或走手工 fallback |
| current = latest | macOS | 启动/手工检查 | 不下载、不弹新版本 |
| preview installed | macOS | 检查 stable/preview channel | 不覆盖 stable feed；按明确 channel policy 升级 |
| wrong hash/wrong signer/missing metadata/offline | macOS | 失败与重试 | 拒绝安装、旧版可用、错误可行动且不泄漏 |
| active chat/bridge/task | macOS | 更新已下载 | 不强退；稍后/下次启动可完成 |

### 渠道晋级与恢复

- 推荐路径仍是先在独立 internal preview channel 验证后再晋级 stable；但用户明确选择本轮跳过实机 RC 验收。最终 stable tag 仍需用户单独授权，CI 必须 fail closed 完成签名、公证、ABI 与资产图门禁；未跑的用户机升级风险在发布汇报中保留。本轮不写入或修改 `stagingPercentage`，也不把 preview 二进制改名后混入 stable。
- updater 本身首个 stable 必须保留手工下载 fallback。更新失败不能阻断应用启动或设置页访问。
- stable 发布前发现问题：阻止渠道晋级并保留 preview 证据。stable 已全量发布后发现严重问题：保留原 tag/Release/metadata，修复后发更高 patch；禁止删 tag、复用版本、修改已发布 metadata 或用旧二进制覆盖资产。
